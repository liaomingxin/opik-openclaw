这个问题值得深入分析。让我从架构、数据模型、边界case、可靠性四个层面来审视。

---

## 📊 整体评价

设计质量总体 **很高**，属于生产级代码。以下几个方面做得很好：
- microtask 延迟 finalize 的时序处理
- flush 指数退避重试
- stale trace 定时清理
- sessionKey 多层回退链
- sanitizeValueForOpik 统一净化

但有 **1 个架构级问题** 和若干中等问题值得讨论。

---

## 🔴 核心架构问题：一次 LLM 调用 = 一个 Trace？

这是最大的问题。先看当前行为，在 `llm.ts:48-53`：

```typescript
// 每次 llm_input 都会 **替换** 同 sessionKey 的旧 trace
const existing = deps.activeTraces.get(sessionKey);
if (existing) {
  deps.closeActiveTrace(existing, `replace active trace`);  // ← 直接关闭！
  deps.activeTraces.delete(sessionKey);
}
// 然后创建新 trace...
```

一个典型的 agent 多轮调用流程：

```
用户发消息 → llm_input①  → llm_output①  → before_tool_call → after_tool_call
           → llm_input②  → llm_output②  → agent_end
```

实际产出的 trace 结构：

```
Trace① (被 llm_input② 强制关闭)
├── LLM Span ✅ (有 input/output/usage)
├── Tool Span ✅ (有 input/output)
└── ❌ 没有 output、没有 success/error、没有 durationMs
    ❌ 没有 agent_end 最终化

Trace② (被 agent_end 正确关闭)
├── LLM Span ✅
└── ✅ 有完整的 output + metadata
```

**问题**：
1. **碎片化** — 一次 agent run 产生 N 个 trace，只有最后一个有完整元数据
2. **丢失关联** — 中间 trace 的 tool 调用和最终结果割裂了
3. **Opik 侧看到大量"半成品" trace** — 没有 output、没有 success 标记

**建议方案：复用 trace，只创建新 span**

```typescript
// llm_input handler 改为：
const existing = deps.activeTraces.get(sessionKey);
if (existing) {
  // 不关闭 trace！只关闭旧的 llmSpan
  if (existing.llmSpan) {
    safeSpanEnd(existing.llmSpan, "new llm turn");
  }
  // 在同一个 trace 下创建新的 LLM span
  existing.llmSpan = existing.trace.span({
    name: `${event.model} #${++existing.llmTurnCount}`,
    type: "llm",
    ...
  });
  existing.lastActivityAt = Date.now();
  return;  // 不创建新 trace
}

// 只有第一次 llm_input 创建 trace
const trace = client.trace({ ... });
```

这样产出的结构就是：

```
Trace (整个 agent run)
├── LLM Span #1 (第一轮推理)
├── Tool Span (工具调用)
├── LLM Span #2 (第二轮推理)
├── Tool Span ...
├── Subagent Span ...
└── ✅ 一个完整的、有 output + success + usage 的 trace
```

## 🟡 中等问题

### 1. microtask 时序假设脆弱

```typescript
// service.ts:601 — agent_end handler
queueMicrotask(() => {
  const current = activeTraces.get(sessionKey);
  if (current && current.trace === traceRef) finalizeTrace(sessionKey);
});
```

假设 `llm_output` 和 `agent_end` 在同一个同步调用栈。如果 OpenClaw 未来改为异步触发（或 hook 执行器内部有 await），microtask 会在 `llm_output` 之前执行 → **usage 数据丢失**。

**建议**：改为显式的"两阶段完成"模式：

```typescript
// agent_end 只标记 "ready to finalize"
active.agentEnd = { ... };
active.agentEndReady = true;
tryFinalize(sessionKey);

// llm_output 也调用
active.output = { ... };
active.llmOutputReady = true; 
tryFinalize(sessionKey);

function tryFinalize(sessionKey: string) {
  const active = activeTraces.get(sessionKey);
  if (!active) return;
  // 两者都 ready 才 finalize，或 agent_end ready 后设置短超时兜底
  if (active.agentEndReady && active.llmOutputReady) {
    finalizeTrace(sessionKey);
  } else if (active.agentEndReady && !active.finalizeTimer) {
    active.finalizeTimer = setTimeout(() => finalizeTrace(sessionKey), 100);
  }
}
```

### 2. 缺少 `session_end` 作为安全网

当前如果 `agent_end` 没触发（bug/crash），只能等 stale cleanup（默认几分钟）。而 `session_end` 能更快捕获到：

```typescript
api.on("session_end", (event, ctx) => {
  const active = activeTraces.get(ctx.sessionKey);
  if (active) {
    // agent_end 没来，session 已经结束了 → 立即 finalize
    finalizeTrace(ctx.sessionKey);
  }
});
```

### 3. `after_tool_call` 的 sessionKey 回退链有隐患

```typescript
// tool.ts:116-128 — 三层回退
if (!sessionKey && deps.activeTraces.size === 1) {
  sessionKey = deps.activeTraces.keys().next().value;  // ← 单一 trace 回退
}
```

**风险**：当有 subagent 时，`activeTraces` 可能恰好只有一个（子代理的），tool 事件会被错误关联到子代理的 trace 上。

**建议**：去掉 "single active trace" 回退，只保留 agentId 和 lastActiveSession 两级。

### 4. `tool_result_persist` 默认关闭不合理

```typescript
if (opikCfg.toolResultPersistSanitizeEnabled === true) {  // 需要显式开启
```

这是一个 sync modifying hook，默认关闭意味着大多数用户不会受益于清理。如果清理逻辑足够安全，应该默认开启。

### 5. `registerCli` 是未文档化 API

```typescript
api.registerCli(...)  // 不在 openclaw-plugin/index.md 的注册方法列表中
```

这意味着它可能是内部 API，未来版本可能移除或更改，有兼容性风险。

## 🟢 小优化建议

### 6. 缺少 `before_compaction` / `after_compaction` 观测

对于可观测性插件，session 压缩事件很有价值：

```typescript
api.on("before_compaction", (event) => {
  // 记录压缩前的 message count → 帮助用户理解 context window 使用
  // 可作为 trace metadata 或独立 event 上报到 Opik
});
```

### 7. Trace 命名可以更有信息量

当前：`${event.model} · ${channelId ?? "unknown"}`

如果改为 per-agent-run trace（上面的核心建议），可以加入更多上下文：

```typescript
name: `${event.model} · ${channelId ?? "cli"} · ${agentCtx.agentId ?? "default"}`
```

### 8. subagentSpanHosts 缺少 size 限制

虽然有 stale cleanup 间接清理，但如果短时间内大量 subagent 创建，Map 会无限增长。建议加 hard cap：

```typescript
if (subagentSpanHosts.size > 1000) {
  // 清理最旧的 entries
}
```

## 📋 优先级总结

| 优先级 | 问题 | 影响 |
|--------|------|------|
| **P0** | 多轮 agent run 碎片化成多个 trace | 核心数据模型错误，用户在 Opik 里看到碎片化的半成品 trace |
| **P1** | microtask 时序假设 | llm_output 与 agent_end 解耦后会丢 usage |
| **P1** | 缺 session_end 安全网 | agent_end 丢失时 trace 长时间悬挂 |
| **P2** | single active trace 回退隐患 | subagent 场景下 tool span 可能关联错误 |
| **P2** | tool_result_persist 默认关闭 | 大多数用户得不到清理能力 |
| **P3** | registerCli 未文档化 | 未来升级兼容性风险 |
| **P3** | 缺 compaction 观测 | 丢失有价值的可观测数据 |

**P0 那个如果改好了，整个插件的可观测性价值会上一个台阶。** 从"每次 LLM 调用一个独立 trace"变成"每次完整 agent run 一个结构化的 trace 树"，这才是 Opik 用户真正想看到的。
